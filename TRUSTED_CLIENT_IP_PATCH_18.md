# Client IP trust: safe default — patch 18

By default, application code does not trust any client-supplied IP header. Requests without a verified IP are identified as `unknown`; raw `X-Forwarded-For` is never used. IP addresses are parsed and IPv6 is canonicalized before use. Audit entries may show `unknown` instead of a client IP.

**Important operational trade-off:** unknown clients share the same rate-limit bucket. With the current application limits, for example, all unknown-IP contact-form attempts share **5 per 10 minutes**, all password-recovery attempts share **3 per 15 minutes**, and reset attempts share **5 per 15 minutes**. Invalid attempts count too. An attacker or ordinary traffic can exhaust these shared limits, causing 429 responses for other visitors. Do not launch a public site under this fallback without considering availability and testing its traffic. Login also has a shared per-account bucket. DB limiter failures still return 503 in production.

`OMNIFLOW_TRUSTED_CLIENT_IP_HEADER` can be set to exactly `x-real-ip` or `cf-connecting-ip` **only after** the operator has confirmed that the actual hosting/CDN/reverse proxy overwrites this one header on every request, that no untrusted client can bypass any proxy in the chain or reach the origin directly, and that there are no alternate paths or workers which can spoof it. The application cannot verify the network peer through the Fetch Request API; setting this variable on its own is NOT proof of trust. A wrong setting lets clients forge IPs, bypass rate limits and falsify audit logs. Missing, malformed, duplicate/comma-separated, port-suffixed or unknown headers result in `unknown` with shared limits. The patch does not modify environment configuration.

Hosting/proxy is not chosen yet, so leave this unset. When chosen: restrict origin network access, configure and verify the exact proxy header using multiple real clients, test direct-origin bypass and spoofed inputs, and use provider WAF/rate controls. IPv6 privacy addresses and changing networks are not stable identities. Trusted Host/canonical domain checks and public lead Origin/CSRF enforcement are separate work; this patch does not implement them. Existing rate-limit rows expire under their normal cleanup; the patch does not modify the database.
